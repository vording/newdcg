# 開発レポート（プロトタイプ v0.1）

## 1. 開発環境の確認
- リポジトリは空（コミットなし）の状態から開始。
- Node.js 22 / npm 10 / Python 3.13 / Chromium（Playwright）が利用可能。

## 2. 技術構成と方針
| 項目 | 採用 | 理由 |
|---|---|---|
| 言語 | JavaScript（ES Modules）+ JSDoc | ビルド不要でブラウザとNodeの両方で同じエンジンが動く |
| 依存 | なし | セットアップ不要、プロトタイプ段階の変更コストを最小化 |
| テスト | `node:test` | 標準機能のみ |
| UI | 素のHTML/CSS/JS | ロジックとの分離を優先。本格化時にReact等やゲームエンジンへ置換可能 |

設計上のポイント：
- **ロジックとUIの分離**：`src/engine` はDOMに一切触れない。UI・AI・テストはすべて `applyAction(state, player, action)` を通して操作する。
- **決定論的な乱数**：シード付き乱数を状態に保存。同じシード＋同じ操作列で同じ結果になる（リプレイ・バグ再現・将来のオンライン同期に有用）。
- **カードはデータ、効果はレジストリ**：カード追加は `cards.js` に1行、新しい効果は `effects.js` に1関数。
- **調整値・未確定ルールは `config.js` に集約**：シミュレーターから設定を切り替えて比較できる。
- **「誰が何を決めるか」を状態で表現**（`state.awaiting`）：相手ターン中の対応（§9）を追加する余地を残している。

将来的にはTypeScript化（カード定義の型チェック）を推奨。カード数が増える前に移行するとコストが小さい。

## 3. テスト結果
- `npm test`：28件すべて成功
  - 初期化（手札枚数・ライフ・デッキ検証・再現性）
  - マナ（増加・上限10・回復・持ち越しなし・後攻も同速度）
  - 召喚（マナ不足・召喚酔い・速攻・配置上限・召喚時効果）
  - スペル（対象選択・不正対象の拒否・回復）
  - 戦闘（ブロックなし・相打ち・蓄積ダメージの持ち越し・ブロッカー制限・行動済み）
  - 勝敗判定、デッキ切れ
  - AI同士200戦：不正アクションなし、全試合決着、カード総数30枚の保存
- ブラウザUI：Playwrightで60手ほど自動操作し、召喚・スペル・攻撃・ブロック・ログ表示を確認（コンソールエラーなし）。

## 4. シミュレーション（AI同士 2000戦）
| 設定 | 先攻勝率 | 後攻勝率 | 平均ターン |
|---|---:|---:|---:|
| 仮置きルール | 49.9% | 50.1% | 21.0 |

## 5. 問題点と改善案
1. **未確定ルールの確定が必要**（[open-questions.md](open-questions.md)）。特にQ2（攻撃後にブロックできるか）はゲームのテンポを大きく変える。
2. **デッキ切れルール未定で膠着しうる**：`'lose'` か `'fatigue'` の採用を推奨。
3. **戦闘後にカードが使えない**：仕様書どおりだが、「攻撃の結果を見てから展開する」判断ができず窮屈。第2メインフェイズの検討を推奨。
4. **同名3枚・30枚ではカードが最低10種必要**：テストに使うカード数が「少数」に収まりにくい。開発中は `config` で枚数制限を緩める運用も可能。
5. **相手ターン中の対応（§9）は未実装**：タイミング整理後に `step: 'response'` として追加予定。
6. **UI**：2人対戦（同じ画面）では手札の受け渡し画面がない。カードの詳細表示・アニメーション・ドラッグ操作は未対応。
7. **AI**：テスト用の簡易AIのため、バランス計測には限界がある。将来はモンテカルロ探索などで強化するとバランス調整の精度が上がる。
